# Workspace authentication and access between computers

This correction applies only to the isolated `rise-roost-beta` Worker and `rise-roost-beta-db`. It preserves every existing workspace, credential hash, design, product, publication, photo reference, and order. It does not change Register/Admin, Supabase, Square, or domain settings.

## What the investigation found

Cloudflare's deployed `PUBLIC_WORKSPACE_ID`, the beta D1 row, and the public `/api/site` response all select the original workspace:

`be1fcd22410ed1f18cab57eddf780aa840c2b2213ab123ae`

At the October 28 investigation there were **103 saved workspaces: this one main website and 102 separate demos**, many generated by automated tests. The main row was created October 27 at 11:46:31 UTC, retained draft/published revision 9, three products, and three orders. Its root website and `/demo/<main-id>` alias read the same publication. Other workspace IDs do not represent another copy of the main website; they have their own documents, keys, sessions, and orders. None were merged or deleted.

All recorded owner sessions were expired when checked. The user also confirmed neither computer was signed in. Studio sessions last **12 hours**. Keeping a page open does not extend or prove server authentication. Keys are stored only as hashes of the workspace ID plus its secret; the original key cannot be recovered from D1. No original key was disclosed, changed, or reset in this task.

The investigation reproduced these routing and sign-in defects:

- One shared `rr_studio` cookie selected whichever workspace most recently signed in or created a demo. Generic `/studio` silently adopted that cookie's workspace. Different computers could therefore open different demos, and switching demos in one browser could displace main-site session selection.
- Studio API requests did not declare the expected workspace. Another tab changing the shared cookie could make a request address the wrong authenticated workspace. Revision guards often rejected this, but did not establish the intended identity.
- Copied access details pointed to generic `/studio`, which did not identify their workspace. Pasting an entire ID/key bundle into one field was not supported. The main sign-in could preload its correct ID while the copied key actually belonged to a private demo. Without the user's secret, the investigation cannot determine which saved pair they hold; the new UI diagnoses mismatched IDs before sign-in.
- The old focus-refresh handler could adopt a different workspace without checking its ID and retained the old workspace's one-time key in its access card. A controlled reproduction using the previous `d55a586` client showed a main ID paired with another demo's key; normal hash verification correctly rejected that copied pair. Only temporary fixtures were used. The new client checks returned IDs and binds/clears key cards by their generating workspace.
- Sign-in relied on input events for field values. Password-manager/Safari autofill can change DOM values without those events. The correction reads the actual fields at submit, and trims surrounding copy/paste whitespace. The ID/key hash verification itself remains strict.
- A stale Studio screen could continue to look signed in after expiration. Failed authenticated operations now show a persistent sign-in notice and retain unsaved edits in the current tab.

## Exactly how to open the correct website

Use this same link on both computers:

https://rise-roost-beta.joshua-maziarz1.workers.dev/studio?workspace=be1fcd22410ed1f18cab57eddf780aa840c2b2213ab123ae

1. On the first computer, open that link. The main workspace ID is prefilled and cannot silently change to another demo.
2. Enter the original **main workspace's** private key and select **Sign in**. Alternatively, expand **Use the saved ID and key together**, paste the complete saved access bundle into **Paste saved access details**, choose **Use these saved details**, then **Sign in**. The bundle is parsed in this tab only, cleared from the paste box, and never put in a URL or localStorage.
3. If the saved bundle names another ID, Studio explicitly says it belongs to a different workspace and offers that workspace's own link. It does not pair its key with the main ID or change any saved site. A demo key cannot unlock the main website.
4. A successful main login shows **BETA WEBSITE · OWNER**. Under **Workspace Access**, the full workspace ID, exact Studio link, and session expiration are visible. **PRIVATE DEMO · OWNER** identifies a separate site.
5. For normal key-based sign-in on the second computer, use the same main URL and matching key. No new workspace is needed.

Do not paste private keys into chat, issues, screenshots, or public links. **Create my private demo** intentionally creates a separate site; it is not recovery.

## Connect another computer without copying a key

This requires an owner who is **currently authenticated to that exact workspace**.

1. On computer B, open the correct Studio URL and choose **Connect from a signed-in computer**. Leave the window open. It displays a temporary code valid for ten minutes.
2. On the already signed-in computer A, open **Workspace Access**, enter that code, and choose **Review connection request**.
3. Verify the workspace and that the code is the one on your own computer B. Confirm the checkbox and choose **Approve this computer**.
4. Computer B connects automatically (or choose **Check connection**). Its URL and workspace ID match A. It receives its own normal 12-hour owner session. The original key is never revealed or reset.

The code is a random 40-bit user code, stored hashed, with rate limits and a ten-minute server expiry. It is not an owner key. Redemption also requires a separate random 192-bit HttpOnly/Secure/SameSite recipient cookie that exists only in the browser that started the request. The exact workspace's valid owner must explicitly approve. A demo owner cannot approve a main request. The approving session must remain valid through redemption; expiry or sign-out blocks it. Grant consumption and session creation commit atomically through D1 batch, with only one claimant succeeding. Used/expired requests do not authorize another session. No reusable access-bearing link is generated.

## If neither computer is signed in

**Device pairing is not recovery for a lost key.** First sign in using the original matching main-workspace pair. If the original key is unavailable or that exact pair still fails, a separate ownership-verification and explicitly approved recovery process is required. An expired cookie, a visible old page, a private-demo key, or an operator's ability to inspect D1 does not establish a new owner session. This release does not create a bypass, rotate credentials, change the main workspace, or reset any saved content.

## Orders and device independence

Public checkout is based on the public site's configured workspace, independently of Studio cookies. It now declares `storefront: "main"`; the server verifies that its workspace matches `PUBLIC_WORKSPACE_ID` and rejects a stale/wrong demo ID without creating an order. Separate demo checkouts stay isolated.

The primary-site fixture test places an order through the root website while another demo is signed in, then verifies it in the main **Orders** dashboard from two independently authenticated owner sessions, including a browser whose generic cookie was subsequently replaced by a demo sign-in. The separate demo's dashboard remains empty. The same account/session/pairing flows are tested over live HTTPS using fresh synthetic demo workspaces. Actual main-site dashboard access requires the owner's valid sign-in; automated tests never mint a main session, change its credential hash, or place/cancel test orders against Danielle's original three orders.

After the owner signs in on both computers, an ordinary beta order placed at https://rise-roost-beta.joshua-maziarz1.workers.dev/ should appear under **Orders → Refresh orders** on either computer with **BETA WEBSITE · OWNER**. Save-draft/publish controls are not needed for order updates.

## Implementation and tests

- Each login establishes a workspace-specific HttpOnly cookie in addition to the compatible legacy cookie. Studio sends an explicit `X-RR-Workspace` on owner API calls. Server authentication validates the session's bound workspace, so cookie names or request headers cannot grant access by themselves. Legacy sessions are promoted only while valid, without extending expiry. Generic `/studio` selects the configured main site and fails closed if its metadata cannot be confirmed; explicit demo URLs remain explicit.
- Sign-out revokes only the selected session/workspace cookies, preserving other signed-in workspace sessions. Existing stored sessions are not deleted. New secure device authorizations use a separate `device_links` table. The additive migration `migrations/0001_device_links.sql` only creates that table; it does not rewrite existing tables or rows.
- `access.test.mjs` covers paired paste parsing, cookie isolation, strict key/ID matching, legacy promotion/expiry, no approval from expired sessions, wrong-owner/CSRF rejection, browser binding, one-time concurrent claims, revocation, expiry, logout isolation, public order routing, and transaction rollback.
- The browser access flow covers wrong-demo cookies, mismatched saved details, explicit device approval, persistent scoped sessions, autofill without input events, two-device Orders, separate demo isolation, and stale-session notices. Device profiles: desktop Chromium, desktop WebKit, iPhone WebKit, Android Chromium, tablet Chromium. These are browser-engine/device emulations; physical-device testing remains owner acceptance.


Local validation: 54 backend tests passed, and the complete 45-case browser suite passed. The focused five-profile authentication flow additionally covers the reproduced copied-credentials failure and default-metadata outages. Existing-data fingerprints were checked before/after the additive migration and deployment; all 103 baseline workspace rows matched, including their credential hashes.
