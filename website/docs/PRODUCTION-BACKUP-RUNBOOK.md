## Daily design and Free-plan constraints

The prepared job uses a private Cloudflare Cron Worker at **07:15 UTC daily** (02:15 EST / 03:15 EDT) to dispatch a restricted GitHub Actions runner. The trigger has no website/database binding, public workers.dev URL, preview URL or HTTP trigger. It makes only the dispatch request; a 204 response means **job accepted**, not **backup successful**.

Bulk exports/encryption run outside the Free plan's 10 ms Workers/Workflows CPU budget. The GitHub workflow uses `workflow_dispatch`, avoiding the 60-day inactivity disabling that affects scheduled workflows in public repositories. The exact protected `main` workflow and approved production source commit must exist before activation. No production deployment is part of the workflow.

The runner:

1. Requests an official consistent D1 SQL export for the configured production UUID. Known preview/beta UUIDs and placeholder IDs are refused before networking.
2. Downloads the short-lived provider export without forwarding its API token or logging the signed URL, restores it into an isolated in-memory SQLite database, then validates its production database/workspace identity marker and required tables.
3. Captures all application tables, authentication records, indexes, views and triggers. Uploaded photos are included from `assets.bytes`; referenced `/assets/...` release images come from the exact approved Git commit.
4. Encrypts the complete snapshot with **AES-256-GCM**, a random 96-bit nonce, authenticated identity/date/key metadata and a SHA-256 integrity check. No raw SQL or customer data is uploaded to Actions artifacts or printed to logs. Temporary runner files contain encrypted archives only and are removed at job completion.
5. Uploads into a **private, production-only R2 bucket**, reads it back, decrypts it and verifies identity/integrity. An archive is never replaced: conditional object creation and stable per-day/key-ID paths make retries safe.
6. Writes a private verification receipt, then sends a data-free success heartbeat to a configured missing-run monitor. A failed/skipped dispatch, export, upload, read-back, integrity check or heartbeat cannot count as a fully successful monitored job.

Normal operations require no Danielle interaction with Cloudflare or GitHub. An operator must establish and maintain the protected deployment, permissions, alerts, recovery keys, credential rotation and periodic recovery drills. GitHub availability, quotas and runner eligibility must be checked for the actual account. Neither scheduler is an absolute guarantee of execution; the independent missing-success monitor must alert on late/missing backups.

## Restore without touching existing data

1. Record the incident, last successful receipt, database UUID, key ID and approved source commit. Obtain operator/owner authorization for any later public recovery. Keep the source archive immutable.
2. Download the chosen encrypted `.rrbk` archive privately. Supply its matching key through a secure environment injection as `RR_BACKUP_RECOVERY_KEY`; never put it in command arguments or paste it into logs.
3. Run `node scripts/restore-business-backup.mjs ARCHIVE NEW_LOCAL_DB EXPECTED_DATABASE_ID` from `website/`. It authenticates the archive before opening a target; refuses existing database/media paths; creates mode-0600 database/media files under a new directory; restores every row, schema object and uploaded blob; verifies record/schema equality; and extracts validated release media into `NEW_LOCAL_DB.media`.
4. Inspect totals, order history, messages, products, photos, pickup deadlines and auth records using isolated tooling. The raw full backup preserves business history and authentication data; it is **not** a clean-production seed or a customer-safe download.
5. A remote D1 import, reidentification of a new database, credential/session rotation, payment-link revalidation, mail/notification replay prevention, and public Worker switch require a separately reviewed recovery procedure and approval. The provided restore command never writes a remote database or updates routing. Do not run an in-place production restore as a drill.
6. D1 Time Travel is an additional recovery layer. An actual current bookmark was retrieved successfully for the preview's modern D1 database. Cloudflare documents **7 days on Free / 30 days on Paid**. An in-place Time Travel restore overwrites the chosen database and cancels in-flight work; it was deliberately **not** run against preview, beta or production. The new production database's own bookmark was retrieved read-only after schema installation. Production restoration remains untested.
